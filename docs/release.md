# Releasing swarfr

The pipeline is rtok's (T43): [cargo-dist](https://github.com/axodotdev/cargo-dist) builds,
signs, tags and publishes; [release-plz](https://release-plz.dev) and a **Bump and release**
workflow decide the version; [`verify.yml`](../.github/workflows/verify.yml) gates both.

## Cutting a release

**Merge the release pull request.** On every push to `main`,
[`release-plz.yml`](../.github/workflows/release-plz.yml) keeps one pull request titled
`release: v<version>` open, with the next version in `Cargo.toml` and its `CHANGELOG.md`
section (the groups of [`cliff.toml`](../cliff.toml), same as `just changelog`). The version is
a patch bump unless a commit since the last tag says `feat` (minor) or is breaking (major).
Merging the pull request — merge commit or squash, so the title is a line of the commit message;
the ` (#123)` GitHub appends when squashing is allowed for — runs `verify.yml` on the merge
commit, then `scripts/release.sh patch --no-bump`, which dispatches **Release** for the version
now in `Cargo.toml` and never raises it.

release-plz reads the `v*` tags to know which version is out (`git_only` in
[`release-plz.toml`](../release-plz.toml)). rtok runs without it, and its release pull request
keeps proposing a version that is already tagged: with `publish = false` there is no registry
copy to compare against. ketch sets `git_only` for that reason.

**Or run Actions → Bump and release.** No version is typed:
[`scripts/release.sh`](../scripts/release.sh) releases the version in `Cargo.toml`, and raises it
(`level`: `patch` by default) only when that version is already tagged — so the first run
publishes `0.1.0`. It lands one `release: v<version>` commit (`Cargo.toml`, `Cargo.lock`,
`CHANGELOG.md`) on `main`, pushes it and dispatches **Release**. The workflow has no dry run;
every green run is a release. The preview is local and writes nothing:

```bash
just release patch --dry-run
```

Both ways end in the same script and the same workflow, so they cannot disagree on the version.
Whichever starts it, the release waits on `verify.yml` — `just check` on Linux and macOS and
`just check-cross` for Windows, the gate `ci.yml` runs on every pull request — and a red gate
means no dispatch, no tag and nothing on the releases page. The gate cannot live inside
`release.yml`: dist runs `host` when `build-local-artifacts` is `skipped`, which is what a failed
`plan-jobs` entry leaves behind, so it would publish a Release with no binaries.

## What a release carries

| Target | Archive |
| --- | --- |
| `aarch64-apple-darwin` | `swarfr-aarch64-apple-darwin.tar.xz`, signed |
| `x86_64-unknown-linux-gnu` | `swarfr-x86_64-unknown-linux-gnu.tar.xz` |
| `x86_64-pc-windows-msvc` | `swarfr-x86_64-pc-windows-msvc.zip` |

Plus `swarfr-installer.sh`, a `swarfr-<target>-update` self-updater per target, `swarfr.rb`
(a Homebrew formula), `source.tar.gz` and `sha256` sums. The release notes end with a
**Download sizes** table. Intel macOS is left out, as in rtok: its runners queue and would set
the release wall-clock.

`.github/workflows/release.yml` is generated by `dist generate` and patched by
[`scripts/dist-generate.sh`](../scripts/dist-generate.sh) — **never hand-edit it**. Change
[`dist-workspace.toml`](../dist-workspace.toml) or [`.github/build-setup.yml`](../.github/build-setup.yml)
and regenerate:

```bash
just dist-generate
```

`dist generate` warns that the `CODESIGN_*` secrets are missing and that the Homebrew publish
job is off. Both are expected: the patch maps the secrets to `MACOS_*`, and the formula is a
release asset only (below).

## Secrets

| Repository secret | Used by | What goes in it |
| --- | --- | --- |
| `RELEASE_PLZ_TOKEN` | `release-plz.yml` | fine-grained PAT, contents and pull requests write |
| `MACOS_CERTIFICATE` | `release.yml` as `CODESIGN_CERTIFICATE` | Developer ID Application `.p12`, base64 |
| `MACOS_CERTIFICATE_PWD` | `release.yml` as `CODESIGN_CERTIFICATE_PASSWORD` | the password of that `.p12` |

The same three as rtok and ketch. `RELEASE_PLZ_TOKEN` is required, not optional: GitHub starts
no workflow from a `GITHUB_TOKEN` event, so a release pull request opened with the default token
has an empty checks list and would merge having never run `ci.yml`. `release-pr` fails with
that explanation when the secret is missing.

`CODESIGN_IDENTITY` is not a secret: on macOS runners `.github/build-setup.yml` imports the
certificate into a throwaway keychain, finds exactly one Developer ID Application identity and
exports it for `dist build`. A missing `MACOS_*` secret fails the macOS job — an unsigned macOS
release is refused. Set them from a machine that has the certificate:

```bash
base64 -i DeveloperID.p12 | gh secret set MACOS_CERTIFICATE -R listepo/swarfr
```

```bash
gh secret set MACOS_CERTIFICATE_PWD -R listepo/swarfr
```

```bash
gh secret set RELEASE_PLZ_TOKEN -R listepo/swarfr
```

Notarisation is off, as in rtok; its `docs/release.md` has the notarytool workflow if that
changes. Signing already covers the installer and `swarfr-update`, which do not set the
quarantine attribute; notarisation would add the archive downloaded in a browser.

## Homebrew

dist builds `swarfr.rb` as a release asset (`installers` includes `homebrew`, `tap =
"listepo/homebrew-tap"`) and does **not** push it: `publish-jobs` stays without `"homebrew"`, so
there is no `HOMEBREW_TAP_TOKEN` here. Pulling the formula into
[`listepo/homebrew-tap`](https://github.com/listepo/homebrew-tap) the way its `sync-rtok.yml`
does for rtok is R7 in `roadmap.md`, with crates.io.

## ketch

[`ketch.toml`](../ketch.toml) is swarfr's ketch manifest, as rtok has one: it names the dist
archive for each host outright and excludes the updater and the source tarball, so `ketch
install listepo/swarfr` cannot pick either. `ketch registry push` sends it to the registry;
`ketch registry validate` on a directory holding `swarfr/ketch.toml` checks it first.
